# Authoring & extending the question bank

Read this **when adding or editing `data/questions.json`**. The core schema + the load-bearing rules
(id append-only, domain/correct/axis) live in `CLAUDE.md`; this file holds the detailed authoring rules
and the full extend-the-bank workflow.

## Authoring rules

- **Balance the correct-answer letter.** When authoring new questions, deliberately vary which letter is correct — never let the correct answer default to the same position (an easy, unconscious habit is keying everything to B). Shuffle each new question's options so `correct` spreads roughly evenly across A/B/C/D, and check the batch distribution before committing: `python3 -c "import json,collections;d=json.load(open('data/questions.json'));print(collections.Counter(q['correct'] for q in d['questions']))"`. If a batch skews to one letter, reorder the options (the option texts are self-contained, so reordering is safe — but then fix any explanation that names an option by letter).
- **Every question needs a real near-miss.** Each question must have at least one distractor (ideally two) plausible enough to make a *well-prepared* candidate hesitate — the tempting wrong answer that reflects a common mental-model error (the "trap" from `axes.md`), not three throwaways with one obvious answer. Concretely: (a) no giveaway where the correct option is the only substantive/reasonable one; (b) avoid the **length tell** — the correct answer must not be the conspicuously longest / most-qualified / most-detailed option while distractors are short stubs (savvy test-takers just pick the longest); keep option lengths comparable. When a distractor pool is all-obviously-wrong (e.g. three "probabilistic" non-solutions against one deterministic answer), replace one with a believable-but-inferior real pattern (e.g. a retry loop, a plausible-but-wrong protocol ordering, a workaround that "works but doesn't scale").
- **Never let the correct option name or justify the tested principle (the "reasoning tell").** Keep every option a flat, parallel *action*; the correct one must NOT editorialize *why* it wins — not by naming the underlying rule (`Enforce them with deterministic mechanisms …`, `… which guarantees the shape`) nor by a virtue clause (`… regardless of what the model decides`, `… so it always holds`, `… the model applies with judgement`) — while the distractors merely describe actions. A prepared candidate then keyword-matches the principle instead of reasoning, and the option asymmetry (one option carries rationale, the rest don't) is itself a tell. The justification belongs in `explanation` ONLY. Concretely: strip abstract-principle vocabulary and `so/because …` rationale clauses from the correct option, describe the concrete mechanism the same way the distractors do (same register, comparable length), and let the test-taker judge which mechanism fits. Sanity check per question: could a reader pick the key from option *wording* alone, without understanding the scenario? If yes, reword.
- **Scope of the balance + length-tell rules — authored questions ONLY.** The correct-answer-letter balancing and the length-tell guidance above apply **only to questions Claude writes from scratch**. Questions imported verbatim from real practice exams are kept **as-is** — never reword, reorder options, or pad/trim an imported question just to even out the answer-letter distribution or option lengths; fidelity to the source is what makes the bank useful for memorising exact wording, and it wins. A mild length skew across the whole bank (the correct option running a little longer than average) is therefore expected and acceptable, because most entries are copied, not generated — do **not** "fix" it by editing imported questions. Only balance *within a new batch you author*.
- **Changing an existing question.** New evidence (a score report, a docs change) shows what else the exam tests; it does not by itself prove an existing question wrong. Before editing, classify: (1) the key contradicts the Exam Guide *in that question's own scenario* → re-key, citing the Guide text; (2) the new evidence tests a different facet → keep the question, add a new one; (3) two facets sit close and the stem blurs them → clarify the stem, keep the key. Re-key only on (1). Examples: q51/q52 were (1) — Guide 5.2 / 5.1 text; q248 was (2)+(3) — `max_tokens` loop handling vs splitting inherently-large output. A re-key also means fixing every `quick-reference.json` row whose `q_ids` include that question.
- **`axis` detail.** The `axis` (1–5) is the ONE axis (from `data/axes.md`) that the question's strongest near-miss distractor trips on — **1** Determinism · **2** Exact-hit · **3** Right-diagnosis · **4** Proportionality · **5** Root-cause/antipattern — assigned by the correct-vs-distractor logic in the `explanation`. The app injects the whole question object, so `axis` powers the dashboard 5-axis tally (computed client-side over the user's misses) and the per-question axis badge in results review; `/ccaf:result` reads it directly instead of guessing.
- **Current count / provenance.** **278** (D1:74 D2:49 D3:59 D4:47 D5:49), all carrying an `axis` 1–5 (backfilled 2026-07 by a classify+verify subagent workflow against `data/axes.md`). Sources so far: exam-1.html, exam-2.html, test-exam.pdf, practice-1 screenshots, owner-authored questions, + cheatsheet gap-fill (2026-07, ids 213–234: CLI system-prompt/`--bare` flags, MCP tool-search/primitives/connection-sequence/templated-resources, escalation payload, batch pilot-test, `detected_pattern`, and several THIN-nuance fills), + axis-1 (Determinism) coverage fill (2026-07, ids 235–240: hook-vs-CLAUDE.md/rules/prompt guarantees, forced/schema-constrained determinism — added because axis 1 was under-represented at 16/234), + prefill / D3 config drill (0.19.1, ids 241–245), + score-report gap fill (2026-09, ids 246–261: loop-exit safeguards, `stop_reason` incl. `max_tokens`, parallel `tool_result`s, handoff authorization state, MCP discovery verification + `${VAR}`, settings permissions vs CLAUDE.md, the five-mechanism choice, `@` references, plan-mode reversibility + review — drafted and adversarially verified by a subagent workflow against official docs; see `maintenance/sources.md` Layer 1b), + second score-report fill (2026-09, ids 262–278: split-and-merge for inherently large output, per-concern review passes, CI review config — standards/tool grant/structured output/permission modes, review exclusions as persistent context incl. a GitHub Actions item, meaningful-vs-trivial tests, dynamic decomposition, subagent-spawn diagnosis, pipeline state manifests, context-window techniques). ## ▶ Extending the bank from a new resource (the common task)
Recommended workflow — this is how the bank was built (multiple sources, deduped; currently **278** questions):

1. **Extract** every question from the resource VERBATIM: stem, 4 options (A–D), the marked correct answer, and the explanation if present. For a big source, dispatch a subagent to parse it (one subagent per source file/PDF parses in ≤20-page ranges) and return structured entries — keeps the main context clean.
2. **Classify domain** with these cues:
   - **1 Agentic Architecture & Orchestration** — agentic loop/`stop_reason`, coordinator↔subagent, Task tool, context passing, Pre/PostToolUse hooks, workflow-enforcement gates, task decomposition, session state (`--resume`/`fork_session`).
   - **2 Tool Design & MCP** — tool descriptions/misrouting, structured errors (`errorCategory`/`isRetryable`), `tool_choice`, tool distribution, `.mcp.json` vs `~/.claude.json`, MCP resources, built-ins (Grep/Glob/Read/Write/Edit/Bash).
   - **3 Claude Code Config & Workflows** — CLAUDE.md hierarchy/@import, `.claude/rules` glob, slash commands vs skills, SKILL.md frontmatter, plan mode vs direct, iterative refinement, CI/CD (`-p`, `--output-format json`, session isolation).
   - **4 Prompt Engineering & Structured Output** — explicit criteria vs vague, few-shot, tool_use JSON schema/nullable fields, validation+retry, `detected_pattern`, Message Batches API, multi-instance vs self review.
   - **5 Context Management & Reliability** — case-facts block/summarization, lost-in-the-middle, trimming tool output, escalation criteria, error propagation, scratchpad/state manifests, `/compact`, stratified sampling/confidence calibration, provenance/claim-source, temporal.
3. **Dedupe against the existing bank:** merge a new question into an existing one ONLY if ≥90% identical (same meaning AND same option set — minor wording differences OK). If the options differ meaningfully, keep both.
4. **Assign ids** = continue from the current max, appended at the end (never renumber).
   **Also assign each new question an `axis` 1–5** (see the schema note in CLAUDE.md + `data/axes.md`): identify the strongest near-miss distractor and name the single axis it fails on, keyed to the explanation. When adding a batch programmatically, a classify+verify subagent pass over `data/axes.md` is the reliable route (that's how the field was first backfilled); for one or two hand-authored questions, just assign it directly.
   **And assign each new question a canonical `task`** — the `"<d>.<n>"` task-statement it tests, a key in `data/task-statements.json` (its domain-prefix must equal `domain`). Match it to the `TASK STATEMENT <d>.<n>` blocks in that domain's `data/tutor-prompts.md` section. This is the ONE place the sub-topic is recorded, so `/ccaf:result` and the tutors look it up instead of guessing — same classify+verify subagent route for a batch (that's how all 240 were backfilled), direct assignment for one or two. If a new question needs a task statement that isn't in `task-statements.json`, that's a content-scope change — stop and reconcile against `maintenance/sources.md` first.
5. **Update `meta`** — bump `total` and the relevant `per_domain` counts.
6. **Validate:** run **`python3 data/validate.py`** — it asserts unique/sequential ids, A–D options, a valid `correct`, a valid `axis` 1–5 and `domain` 1–5 on every entry, a canonical `task` (a key in `data/task-statements.json` with a matching domain-prefix) on every entry, that `meta.total`/`meta.per_domain` match reality, and that no entry contains `</script>`/`<!--` (which would break the injected HTML app). It also prints the correct-answer-letter distribution and warns on a heavy skew — don't let a new batch skew to one letter.
7. **Sync the Cheatsheet to the new questions.** Run **`python3 maintenance/reference-coverage.py`** — it flags every new bank question not yet reflected by a `quick-reference.json` row. Close those gaps with the **`maintenance/reference-sync.workflow.js`** generator (scope it by domain or `sections`, e.g. the tasks your batch touched): it drafts, per section, `q_ids` to attach to existing rows + new `see → answer` rows for uncovered nuances, adversarially verified. It **edits nothing** — review the returned patch, apply the rows by hand into `quick-reference.json` (keep exam wording/API tokens English), then re-run `python3 data/validate.py` + `python3 maintenance/reference-coverage.py`. Section 2.6 is the hand-authored golden shape to match. (Also: if the batch changed a core rule, update the matching `exam-traps.md` line so the projection doesn't drift.)
8. **Bump the plugin version** in `.claude-plugin/plugin.json` (and marketplace.json) — teachers and `/ccaf:dashboard` pick up new questions automatically; no code changes needed.
